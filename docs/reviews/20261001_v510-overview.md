## 1. Executive summary

The v501–v510 batch is well specified and integrated: every slice has a spec, plan, as-built record, and lifecycle entry; the combined fast CI gate passed; and the ten temporary worktrees were checked against their handoffs before cleanup. The batch improved combat feedback, ground loot readability, town and dungeon presentation, and server-authoritative boss/Ranger mechanics. The client bot suite and headless smoke passed in the extended run.

The most important remaining correctness risk is not visual: realtime input is made available to the simulation before the durable append succeeds. A failed write can therefore produce gameplay that the replay log cannot reproduce. It needs a focused design and failure test before changing input-acceptance behavior. The review also found that a cold CI run can skip DB-backed Go tests before Postgres is started. That CI ordering defect has a small, bounded fix and is the first `$refactor` task.

`make ci-full` is not green yet. It reported one `teleporter_lab` failure; the isolated rerun passed. Treat that as a non-reproduced full-run failure, not a green extended gate. No performance claims are inferred from passing visuals or bot scenarios.

## 4. Top 10 recommendations

Tags: **[minor]** safe for the current `$refactor`; **[future-plan]** requires design or a larger coordinated change; **[future-slice]** should be scoped with gameplay/client acceptance.

1. **[future-plan · Correctness] Make input acceptance durable before the sim can consume it.** Specify what the client sees on append failure, then test the failure path through replay. `session_loop.go:365-395`, `session_tick.go:10-22`.
2. **[minor · CI reliability] Start and ensure Postgres before DB-backed Go tests; fail the gate if provisioning fails.** Current step 6 can unset the test DB and pass before step 8 starts Postgres. `scripts/ci.sh:314-340`, `scripts/test_db.sh:36-59`.
3. **[future-plan · Replay safety] Propagate cancellation through replay and set an explicit maximum timeline horizon.** The current non-negative `int64` request can drive a huge loop; the maximum is a policy choice. `replay.go:265-295`, `http/inspect.go:180-189`.
4. **[future-plan · Determinism] Pin rules/content revision and gameplay-debug mode in session reconstruction inputs.** Current rules and environment can vary across a replay. `sim.go:522,898-904`; replay reconstruction paths in `replay.go`.
5. **[future-plan · Contract tests] Apply strict v8 schema validation to reconnect snapshots, not only scenario-stream snapshots.** `ci.sh:396-402`, `tools/bot/run.py:2867-2880`.
6. **[future-plan · Contract tests] Add a Go JSON-tag/schema drift gate for v8 serialized types.** Existing validation checks schema presence and selected invariants, not Go serialization parity. `tools/validate_shared.py:339-389`.
7. **[future-slice · Client correctness] Prove reconnect during an active boss warning restores the active lane and phase timer.** Ordinary reconnect coverage is not the live phase case; v509 as-built keeps it partial.
8. **[future-plan · Client cohesion] Extract a typed event router from `main.gd:_apply_delta` with event ordering and state synchronization tests.** `client/scripts/main.gd:1308-1784`.
9. **[future-plan · Tooling cohesion] Split bot step dispatch and shared catalog validation into typed, domain-owned modules.** Keep narrow tests and avoid a mechanical `helpers=globals()` split. `tools/bot/run.py` (4,534 lines), `tools/validate_shared.py` (3,170 lines).
10. **[future-slice · Evidence] Close the v506/v508/v509 resident-memory, final-state cost, hands-on readability, and boss reconnect evidence gaps.** Keep capture, functional, and measured performance claims separate.

## 5. What “done well” looks like here

- A green fast CI gate is reported separately from a failed or unrun extended gate; an isolated retry is additional evidence, not a replacement result.
- New replayable gameplay is accepted only when the durable input/event record and reconstructed state agree under write failure and reconnect.

- Every coordinated slice is represented by a spec, plan, as-built note, lifecycle entry, and a reviewable isolated-worktree handoff.
