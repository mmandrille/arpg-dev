## 1. Architecture

**[Strength] The authority boundary and intent-registry discipline both held through this window.** No new `case` was added to `applyInput` (`sim.go:1101`); the v488 stash-sync system input was wired entirely through the existing `inputHandlers`-adjacent `inputdecode` package (`inputdecode/system.go`'s `decodeStoredSystem` gained one `if` branch dispatching to `decodeStoredAccountStashSync`), following the same "absent from `IsClientIntent`/`Decode`" pattern as the v476 load-shed input. `handleClientMessage` still overwrites `ActorPlayerID` from the connection (`session_loop.go`).

**[Fixed, real] Client-chosen tick is bounded.** `realtime/input_tick.go`:
```go
const maxClientTickLead uint64 = 2
func scheduleClientTick(requested, cur uint64) uint64 {
    if requested < cur || requested > cur+maxClientTickLead {
        return cur
    }
    return requested
}
```
`session_loop.go:372` now calls this instead of the old `if tick < cur { tick = cur }` one-sided clamp. `TestFarFutureClientTickIsRecordedAtCurrentTick` (`input_tick_test.go:35`) drives a `tick: 1_000_000_000` envelope end-to-end through `handleClientMessage`, confirms the persisted row is at the current tick, and then runs `replay.Verify` to prove the session still replays clean. This closes the practical attack: a session can no longer be poisoned with an unbounded future tick via the input path.

**[Unresolved — High, carryover] Mercenary roster still reads/writes live DB rows during replay and build.** `mercenaryroster/load.go:18-46` (unchanged since v486 except a gofmt realignment — see `git diff 2cf0dcd1..HEAD -- server/internal/mercenaryroster/load.go`, which shows only field-alignment whitespace and the addition of an unrelated `HiredMercenaryCharacterID` passthrough):
- `repo.ListCharacters(ctx, accountID)` reads the account's *current* alt-character rows and filters on the live `Dead` flag — an alt that died or levelled since a session started changes the hire roster on resume/replay.
- `repo.GetOrCreateCharacterProgression` is still called from this path, so replay and the debug `/state` endpoint still write to the DB.
- This is the same gap the v486 backend report flagged as "High, still open" and listed as Top-5 #3 (bundled with the debug-flag and rules-version fixes). Only the debug-flag half of that recommendation shows up in PROGRESS.md's "still open" line for the v486 review; the mercenary roster half is undocumented there. **Recommendation: add an explicit PROGRESS.md open-gaps line for this, separate from the debug-flag one, so it isn't lost again.**

**[Unresolved — Med, disclosed] Gameplay-debug mode is still an unrecorded env read.** `sim.go:520` still calls `gameplayDebugEnabledFromEnv()` (`sim.go:896-903`) at construction time, before town presets are placed, and `SetGameplayDebug` is still applied *after* `Reconstruct` on resume (`session_loop.go`), which is the same re-seed-and-reallocate-IDs hazard as before. The new `//nolint:determinism known gap (v486 review): debug mode is not yet recorded on the session` comment on `sim.go:897` is the one honest acknowledgment in the codebase that this is unfixed — it stops the lint from silently exempting it as "safe" and instead marks it as known debt.

**[Unresolved — Med] No rules/content version pinned to a session; `buildSessionSim` still uses `Reconstruct`, not `Verify`** (`session_loop.go`). Unchanged since v486; `grep -r "rules_hash\|rules_version" internal/ migrations/` still finds nothing.

## 2. Technical

**[Fixed, real] Determinism lint now covers all of `game/`.** `cmd/determinism-lint/main.go` runs against `./internal/game/...` (confirmed by direct run: `determinism-lint: OK (78 grandfathered map-range sites in 23 files)`, exit 0). The baseline file (`.maintainability/determinism-baseline.tsv`) lists 23 files far beyond the old `sim.go`/`handlers.go` pair — `rules.go` (26, the largest), `shop.go` (6), `item_roll_upgrade.go` (4), etc. — which is direct evidence the pass now walks the whole package, not just the two hot-path files. The two specific v486-cited hazards are fixed with sorted iteration and an explanatory comment each:
- `skill_aim_nav.go:21`: `for _, id := range sortedEntityIDs(level.entities)` with a comment ("Sorted IDs: equal-distance candidates must tie-break by entity ID, not map order").
- `unique_chest.go:240-244`: nested `sortedLevelNums()` / `sortedEntityIDs()` before the `s.alloc()` calls, with the matching comment.

**[Fixed, real] gofmt and `-race` are CI gates now.** `scripts/ci.sh` step 6: `make fmt-check-go && cd server && go test ./... && go test -race ./internal/realtime/... && go vet ./...`. `gofmt -l server` returns nothing. The `-race` scope is honestly commented as partial: `internal/http` is excluded "exceeds the 10m test timeout under -race, so it is not included yet" — this is a real, if incomplete, improvement over v486's "no race detector at all."

**[Fixed, real] Replay-critical persistence errors are now surfaced.** `session_admission.go:29` and the disconnect path now check the `SetSessionMemberConnected`/`Disconnected` error and meter it (`eb0f9928`), with `member_persist_errors_test.go` asserting the `PersistenceErrors` counter increments on a forced failure.

**[Fixed, real] DB-backed tests fail instead of silently skipping when a test DB is configured.** New `internal/testdb` package: `SkipOrFail` fails the test when `ARPG_TEST_DATABASE_URL`/`ARPG_DATABASE_URL` is explicitly set and unreachable, and only skips on the bare local dev fallback. This directly targets the v486 finding about `store_test.go:33`/`ws_test.go:40` silent skips.

**[Unresolved, carryover] Tick-path DB calls still use `context.Background()`.** `persist_batch.go:58`, `session_loop.go:392,520`, `member_lifecycle.go:91` — all unchanged. A stalled Postgres still freezes every session tick with no bound.

**[Unresolved, carryover] No WebSocket frame/rate limits.** `hub.go`'s `CheckOrigin` still returns true unconditionally; no `SetReadLimit`, no per-client rate limit. Unchanged — acceptable at dev-token-auth maturity, as before.

**[Unresolved, mitigated] Replay has no max-tick/ctx guard, but the practical risk is now much smaller.** `replay.replayTicks` (`replay/replay.go:262-310`) is unchanged: no `ctx` parameter, loops `for t := int64(0); t <= throughTick`. Since the only known path that could *produce* an unbounded `throughTick` (the client-chosen input tick) is now clamped to `cur+2`, this is now defense-in-depth rather than an open exploit — but it is still correctly listed as open in PROGRESS.md, not glossed over.
