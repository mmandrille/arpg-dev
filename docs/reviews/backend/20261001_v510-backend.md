## Summary

The batch preserves the server authority boundary. v509 resolves boss attack lanes and damage on the server, and v510 derives the Ranger passive from effective Dexterity using shared rules. Replay and bot coverage exercise those mechanics. The v500 mercenary roster replay leak was fixed before dispatch: immutable session-start snapshots include roster identity, death state, progression, and items, and reconstruction no longer reads roster rows from the live database. The security review of the eleven Ranger server files found no blockers or new trust boundary; it evaluated state validation, arithmetic bounds, and explicit skill eligibility.

One high correctness risk remains in the existing realtime input path: the session loop puts input into the sim buffer and advances its durable watermark before appending the record. If persistence fails, the loop logs the error and later ticks may consume an input that replay cannot reconstruct. This predates the presentation batch and is not covered by the successful-append tests.

## 1. Architecture

**Strength — authoritative combat.** Boss lane timing and safe-lane selection are server-authored; collision and hit resolution use the locked world-space lane. Ranger affinity is applied server-side from effective Dexterity and an explicit eligible-skill set. The replay, snapshot, and bot scenarios cover the new contract.

**High — live input may be consumed before durable recording.** `session_loop.go:365-395` adds to `l.buffer`, calls `noteDurableLocked`, releases the lock, and only then calls `AppendInput`; an append error only increments a metric and logs. `session_tick.go:10-22` can consume that buffer on the next tick. A failed database write can therefore leave accepted gameplay absent from the replay log. Define the intended acceptance and rollback/backpressure semantics, then add an append-failure replay regression before changing this path.

**Medium — content and debug mode are not fully pinned to a replay.** Reconstruction uses the currently loaded rules, while session creation does not persist a rules/content revision. `sim.go:522,898-904` also enables debug behavior from process environment; resume reconstructs before any session-specific correction. A content reload or environment change can make an old session reconstruct differently.

## 2. Technical

**Medium — replay work has no caller cancellation or practical horizon.** `replayTicks` loops from tick zero through the requested tick (`replay.go:265-295`) without a context check. The local replay timeline accepts any non-negative `int64` (`http/inspect.go:180-189`); `MaxInt64` also overflows the loop counter after its final iteration. Context propagation is mechanical, but selecting a maximum accepted horizon is a policy decision and should be specified.

**Medium — database work can hold the session lock or stall a loop.** `attach` and `detach` perform member persistence around the session lock (`session_loop.go:150-200`); periodic persistence uses `context.Background()` (`session_loop.go:519-520`). Bound these calls and separate slow I/O from state-lock ownership without changing reconnect ordering.

**Resolved — v500 mercenary replay/database leak.** Session start snapshots now freeze the mercenary inputs used in replay. The replay path no longer asks the live roster loader for the current alternate-character rows (`server/internal/store/session_start_snapshot.go:11`, `server/internal/mercenaryroster/load.go:10`, `server/internal/replay/member_setup_replay_test.go:94`).

## 3. Maintainability

`sim.go` remains a 6,590-line coordinator, essentially flat from v500. The current review did not find a safe extraction that can be completed as a small no-behavior-change commit; simulation ownership and replay invariants make broader splits a planned maintenance project.

## Top 5 backend refactors

1. Define and test durable input acceptance when `AppendInput` fails; preserve the no-unrecorded-gameplay invariant.
2. Propagate request cancellation through replay and specify a bounded timeline horizon.
3. Pin replay inputs to the session's rules/content and gameplay-debug configuration.
4. Put deadlines on session persistence and move database waits out of critical session-lock sections.
5. Plan further `sim.go` extraction around explicit ownership boundaries and replay equivalence tests.
