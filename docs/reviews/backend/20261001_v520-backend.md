## 1. Architecture

- **[Strength] Authority and deterministic boundaries remain intact.** No server or protocol changes occurred. Client additions consume existing snapshots/events and affect rendering only; the wall fixture adds no server behavior.
- **[High] Live input can be consumed before durable persistence succeeds.** `session_loop.go:370-395` appends to the in-memory tick buffer and advances its durable marker before `AppendInput` completes; append failure only logs/records a metric. `session_tick.go:12-22` drains the buffer independently. A failed write can therefore produce live state that replay cannot reconstruct. Define acceptance/failure semantics and cover the append-failure path before altering the ordering.
- **[Med] Replay has no practical horizon or cancellation check in its tick loop.** `replay/replay.go:262-295` iterates through the requested tick; `http/inspect.go:180-189` accepts any nonnegative `int64`. Very large requests can consume unbounded work, and the loop boundary can overflow. Bound the horizon and propagate context.
- **[Med] Replay does not pin all authoritative inputs.** Replay construction uses currently loaded rules and `ARPG_GAMEPLAY_DEBUG` (`game/sim.go:511-523,898-904`; `replay/replay.go:236-259`), so later config changes can alter reconstruction.
- **[Med] Detach persistence runs under the realtime session mutex.** `session_loop.go:177-196` performs persistence while locked; the helper uses a background context (`session_admission.go:36-42`). A slow DB operation can delay session work. Define bounded persistence while preserving disconnect ordering.
