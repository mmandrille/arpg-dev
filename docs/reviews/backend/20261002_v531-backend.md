## Summary

The server remains the authority for simulation, generation, and persistence; dungeon layout and encounter choices are driven by shared generation rules and deterministic seed/depth inputs. The v522–v531 additions have explicit topology, reachability, door, pack-placement, and multi-seed audit coverage. The coordinator's repeated 240-floor report was byte-identical and recorded zero generation failures or invariant findings. This static pass found no concrete high-severity defect in the new dungeon-generation paths.

The highest risks remain replay work and durability. The timeline endpoint accepts an arbitrary nonnegative tick and the reconstruction loop can run effectively without bound; a `MaxInt64` limit can also wrap the signed inclusive loop. Inputs are placed in the live simulation buffer before database append completes, while persistence errors only log. Replay also reconstructs with current rules rather than a version pinned to the session. A separate security concern is raw database/replay errors reaching server logs.

## 1. Architecture

- **[Strength] Server authority is preserved.** Generation and encounter selection live in `server/internal/game`; client presentation consumes authoritative state. The dungeon helpers separate room layout, reachability, wall/door output, and encounter composition (see `docs/CODEMAP.md:16`).
- **[Med] Replay reconstruction is not version-stable.** Session persistence stores seed/world but no rules/content revision (`server/internal/store/models.go:44-55`); reconstruction takes the current rules at `server/internal/replay/replay.go:89-118,243-252`. A future rules edit can change the result for a historical session.
- **[Med] Live input acceptance and durable history can diverge.** `handleMessage` adds input to the in-memory buffer before `AppendInput` (`server/internal/realtime/session_loop.go:370-375,392-395`); the simulation may consume it before persistence succeeds.

## 2. Technical

- **[Med, CWE-400/CWE-835] Replay timeline work is attacker-controlled and unbounded.** The owned-session timeline handler accepts every nonnegative int64 `through_tick` (`server/internal/http/inspect.go:180-189`), `BuildTimeline` promotes it directly to `maxTick` (`server/internal/replay/replay.go:159-160`), and `replayTicks` loops inclusively with signed `t++` (`replay.go:286`). A very large value can monopolize CPU; `MaxInt64` can wrap and continue indefinitely. Ownership checks do not bound the work.
- **[Med, CWE-532] Infrastructure details may be logged.** Raw `AppendInput` errors are logged by the realtime loop and member lifecycle (`server/internal/realtime/session_loop.go:392-395`, `member_lifecycle.go:91-94`); the repository wraps the DB driver error (`server/internal/store/repos.go:2084-2097`). Replay logging writes `err.Error()` (`server/internal/http/inspect.go:201-208`). Map to a stable error class or sanitize before logging.
- **[Strength] Determinism has explicit guardrails.** `make lint-determinism` passes with 77 documented grandfathered map-range sites; the dungeon audit and focused generation invariants add evidence for deterministic output and traversability.
- **[Evidence limit]** The opt-in generation audit is deliberately report-only (`server/internal/game/dungeon_generation_audit_test.go:20-22`). Its final integrated report had 240/240 generated floors and zero findings, while the existing progression sweep remains fail-fast. The audit itself is not a CI regression gate.
