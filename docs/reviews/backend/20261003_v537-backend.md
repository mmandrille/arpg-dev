## Summary

The batch kept the authoritative boundary intact: collision for decor moved to the server (`kind prop` walls) instead of being faked in the client, wider passages are guarded by a data-owned floor, and every new generator draws from its own seeded stream. The weak spot is not the new code but what wider/more-crowded layouts exposed in older code: distance-scaled path-search budgets, a 1.0 nav grid, and generation/test cost near Go's default timeout.

## 1. Architecture

- **[Strength] Props reuse the wall channel, not a new entity type.** `placeDungeonProps` (`dungeon_props.go:12`) emits `wallObstacle{kind: prop, propID}`; collision, pathfinding, reachability, wall deltas, snapshots and replay needed no new path. `WallView.PropID` is the only wire addition.
- **[Strength] Prefix invariance is enforced.** `placeDungeonProps` runs last (`dungeon_room_layout.go:87`) on its own stream (`seed|props|level|attempt`); `TestPropsDoNotChangeEarlierGenerationAndAreDeterministic` proves props-off equals props-on minus props.
- **[Med] Overloading `walls` with clutter has a cost.** Debug/bot counters and any consumer that filters only by `source`/`kind` now see props (`generated` source). The client filters `kind==prop` explicitly for floor tiles and corners, but this is convention, not type safety. Consider a distinct `props` list in the wall view if more clutter kinds arrive.
- **[Low] `rules.go` still grandfathered and drifting (2,836 vs baseline 2,813).** The clearance validation call was moved into `validateDungeonGenerationExtendedRules` (`dungeon_generation_rules.go:32`) to avoid growth; the struct field and copy still added 2 lines.

## 2. Technical

- **[High] Path-search budget scales with straight-line distance, not detour.** `player_navigation_budget.go:62` uses `dist*320 + 64` nodes. In wide layouts a door or stair behind a long detour returns `no_path`. Evidence (runtime): before the approach fix 5 of 6 `room_doors` seeds failed `no_path`; after it, seeds 00/01/02/04 still fail on the long walk to the stairs (baseline `main` also fails 4 of the same 6 seeds, for door-less layouts or detours). Real players clicking a far door in a big floor can hit this.
- **[Med] The 1.0 nav grid makes opening width alignment-dependent.** A 2.25 gap can leave one walkable column of cell centers (ASCII evidence in the v535 as-built; old 2.0 gaps had the same property). `validatePassageClearance` (`dungeon_passage_clearance.go:18`) checks world widths, not nav-cell width, so the floor cannot guarantee two-cell passages (that needs ≥ ~2.9).
- **[Med] Approach goal used cell corners while the player stands at centers.** Fixed for melee/interactable approaches (`approach.go:59`); the ranged approach path (`findRangedApproachGoal`) was not audited and may share the corner convention.
- **[Med] Generation is slow.** Isolated `go test ./internal/game` took 596 s (default timeout 600 s); a single level generation is ~1.7–3.7 s; the strict 240-floor audit took 815 s. v536 added ~6% (L-1) to ~30% (L-4) before the reachability-grid reuse (`dungeon_reachability_grid.go:45`) cut it. CI now passes `-timeout 20m` (`scripts/ci.sh:326`, `make/server.mk:10`), which hides the trend.
- **[Strength] Door sealing is rule-checked.** `doorBarrierSealsOpening` (`dungeon_door_rules.go:90`) requires a centered closed door to leave < one player diameter per side, so the 1.6 barrier legitimately seals gaps up to 3.4 and the lab geometry (`door_lab`) stays valid.
- **[Low] Props footprints are conservative squares (1.2–1.4)** because yaw is a client choice; collision exceeds the model on one axis for the table and the barrel stack.

## 3. Maintainability

- New code lives in focused files (`dungeon_props.go` 106 lines, `dungeon_props_rules.go`, `dungeon_passage_clearance.go`) with direct tests; no `helpers=globals()` coupling added.
- **[Med] Tests were locked to layout in three places** and had to be repaired: a pinned `{10 8}` profile override, a single pinned seed for the elite-chest test, and the obstacle golden's door-target reachability (a closed door blocks its own grid cell, so door targets were unreachable by construction). Fixes derive from rules or sweep seeds; `shared/golden/dungeon_obstacles.json` is regenerated and its schema enum gained `prop`.
- **[Low] `TestPlaceRoomCorridorLayout_SeedSweepAlwaysGenerates`-style sweeps dominate runtime** (single subtests up to ~77 s). Tag or split them rather than raising timeouts further.

## 4. Documentation

Specs, plans and as-built exist for all five slices with honest limits (no real-floor prop frame, flaky windowed capture, stale frame-pacing probe). The v535 as-built records the width bisect (2.5/3.0 broke deep floors; 2.9–3.0 broke long routes; 2.25/2.4 chosen) which is the most useful artifact for the next retune.

## Top 5 backend refactors

1. **[future-plan · High]** Make player path search detour-aware (budget from a bounded-radius flood or path length hint) or add hierarchical/room-level routing; cover with a wide-layout long-route test.
2. **[future-plan · Med]** Add nav-aware passage validation (count walkable cells across each corridor/door at generation) or a finer nav grid.
3. **[minor-commit · Med]** Audit `findRangedApproachGoal` and other goal builders for the corner-vs-center convention; add a test beside `approach_cell_center_test.go`.
4. **[future-plan · Med]** Split heavy generation sweeps behind a build tag/`-short` and report per-test time in CI so runtime drift is visible before the timeout.
5. **[future-plan · Low]** Give props their own wall-view list (or a typed `kind` category) so non-structural obstacles cannot leak into structural consumers.
