## Summary

The client got thinner: it no longer plans decor. `DungeonRoomDressing.plan` and its helpers are deleted and props arrive as server walls; the renderer maps `prop_id` to a model and batches them. Camera and tooltip changes were data/presentation only. Remaining risk is harness fragility for windowed proof and a few stale fallbacks.

## 1. Architecture

- **[Strength] Authority boundary improved.** `placements_from_walls` (`dungeon_room_dressing.gd:21`) uses server positions; only model/scale/yaw (stable hash of the wall id) are presentation.
- **[Strength] Cross-stack parity is asserted.** `test_dungeon_room_dressing.gd` checks the client catalog covers every server `prop_id` and that each model's extent matches its server footprint within tolerance; `tools/validate_dungeon_props.py` repeats the id check in CI.
- **[Med] Structural vs clutter is by convention.** `WallRenderer.render_wall_layout` filters `kind==prop` before corners/floor planning, but `main.gd` helpers such as `_non_perimeter_wall_count` and bot/debug counters count props as walls, which can mislead scenario assertions.

## 2. Technical

- **[Med] Tooltip lost the tooltip-level non-hue rarity cue** with the preview removal; text line, colored name and border remain and the hovered slot keeps its v508 cue (accepted in the v532 spec).
- **[Low] Dead `setup` parameters** (`_item_presentations`, `_fallback_label`) kept for positional compatibility across ~11 call sites (`item_tooltip_panel.gd:17`).
- **[Low] Camera fallback literals are stale** (12/8/20 in `player_camera_controller.gd` near lines 109–127 and 279) against data 15/8/25; they only apply when data is missing, but they will mislead a reader and a replay-zoom test pins the old default through a stub config.
- **[Med] Windowed `capture_frame` is flaky on this host:** `generated_entrance_frames` timed out three times at the first capture and passed on the fourth; the PNG was written in the failing runs, so the step's completion signal, not rendering, is the suspect (`bot_frame_capture.gd`).
- **[Strength] Draw-call budget held.** Props use one MultiMesh per asset; the fixture room reports 4 instances / 84 draw calls; zoom-out cost +10 draw calls (+8%) in a live snapshot (single run each, not a controlled A/B).

## 3. Maintainability

- `main.gd` shrank slightly by deleting the deferred dressing refresh and `floor_key`/anchor plumbing; `wall_renderer.gd` is at 576 (96% of the new-file target, still under 600).
- No `helpers=globals()`; the new capture driver for tooltips follows the character-screen driver pattern; showme suite registry and tests are in sync.

## 4. Documentation

`docs/as-built/assets/v532..v537` retain before/after and real-play frames with explicit limits. The v537 frames show doors, walls and a corridor mouth on real floors but **no prop in view** (spawn clearance plus the movement contract), which is stated plainly.
